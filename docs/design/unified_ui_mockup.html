WITS & FOOLS — ONE UI, EVERY SCREEN

A single responsive layout and one asset set for desktop and mobile. The board is built once; the layout reflows by aspect ratio, and the input layer (hover vs tap) is chosen at runtime by pointer capability — not by a separate codebase.

The unification thesis — why one layout, not two

The mobile design's discipline (compact identity chips, edge-docked reference, one thumb-zone action, the race meter always visible) is exactly what the crowded desktop board needed. So instead of maintaining two UIs, the mobile layout becomes the base and desktop is the same layout with the breakpoints opened up — chips expand into panels, the log undocks into a rail, cards and spacing grow. Everything below the layout — scene, prefabs, card art, fonts, data bindings — is shared verbatim.

ONE SCENE, ONE ASSET PATH

Same GameScene, same CardView prefab, same Resources/CardArt, frames and fonts on both platforms. There is no /mobile vs /desktop fork to keep in sync.

HEIGHT DRIVES LAYOUT

A single ResponsiveLayout picks a tier — Compact / Comfortable / Spacious — keyed on viewport height first (a card game must stack opponent + bout + hand + action vertically); width only gates the desktop expansions. So a wide-but-short window stays Compact instead of cramming desktop chrome into 360px. Portrait is landscape-locked; ultrawide is clamped & centered.

POINTER DRIVES INPUT

A single InputProfile reads pointer capability: a fine pointer enables hover tooltips & lift; a coarse pointer enables tap-to-inspect. Same CardView, same handlers — only which affordances are live differs.

Input: hover (desktop) and tap (mobile) on one component — chosen at runtime, not built twice

The same CardView answers both. The difference is only which affordance fires: a fine pointer reveals the card's detail on hover and plays on click; a coarse pointer reveals it on tap (the hover-equivalent) and commits on a second tap or an action pill. Inspect-before-commit is preserved on both — desktop just gets it for free via hover.

How it maps to Unity — concrete implementation

RESPONSIVE LAYOUT (geometry)

  • CanvasScaler: Scale With Screen Size, reference 1280×720, matchWidthOrHeight biased to height — vertical space is the tight constraint (phone-landscape is only ~390pt tall), so the board scales to fit height and never clips top/bottom. Pair with a max play-width so ultrawide pillarboxes instead of stranding.
  • ResponsiveLayout MonoBehaviour on the Canvas: on start and on OnRectTransformDimensionsChange, compute tier from height first (Compact ≤520, Comfortable ≤699, Spacious ≥700 and width ≥1100), lock to landscape when width<height. Width only gates the Spacious expansions — never re-tiers a short window into desktop chrome.
  • The tier sets a handful of values the existing widgets already read: card scale, edge padding, chip-vs-panel mode (toggle the subtitle + race label objects), log button vs docked EventLogPanel, bout slot spacing, safe-area insets.
  • No new screens, no duplicated prefabs — it only moves/sizes/toggles what SceneBuilder already creates.

INPUT PROFILE (interaction)

  • Detect once: Application.isMobilePlatform || (Input.touchSupported && !Input.mousePresent) → Touch; else Pointer. Re-evaluate if a mouse appears (hybrid devices).
  • CardView keeps its OnPointerEnter/Exit (hover) and OnPointerClick handlers. In Pointer mode, enter→show tooltip+lift, click→play. In Touch mode, enter is ignored, first click→select+inspector+pills, pill/second tap→commit.
  • Hit targets: the Touch profile applies the Compact/Comfortable tier minimums (≥44pt) automatically via the layout tier; Pointer mode can pack tighter.
  • Both paths funnel into the same TryAttack/TryDefend/TryUseAbility — the engine never knows which input drove it.

Tier and input are independent: a touchscreen laptop in a small window is Comfortable + Touch; a phone mirrored to a monitor with a mouse is Spacious + Pointer. They compose, they don't fork.

WHAT THIS FIXES FROM THE OLD DESKTOP BOARD

  • Crowding → the mobile chip discipline removes the scattered labels; desktop spends its extra room on spacing and a docked log, not more widgets.
  • Two code paths → collapsed to one layout + two small policy objects (ResponsiveLayout, InputProfile).
  • Asset duplication → none; a card is one prefab and one art file, scaled by a layout variable.
  • Hover-only information on desktop → also reachable by tap on mobile (the inspector is the hover tooltip's touch twin), so no platform loses information.
